# v3.4.3 Design Spec: Targeted Observability & Operator UX

**Date:** 2026-03-15
**Status:** Revised
**Scope:** Patch release - small, additive changes only
**Theme:** Make existing lock, exit-code, and runtime controls easier to see, understand, and operate

## Motivation

v3.4.0-2 added the major org-report, trending, and automation features. The current codebase already has several relevant control points in place:

- Circuit breaker protection
- Org-report concurrency locks with `fcntl` / lease backends
- Lease-backend heartbeat and lock-loss detection
- JSON/text logging with contextual logger adapters
- Machine-readable run summaries
- Lightweight CLI fast paths in `__main__.py`

The v3.4.3 patch should improve observability around those existing behaviors without redesigning the batch scheduler, cross-process execution model, or logging handler topology.

One important accuracy note: the current API auto-tuning code records worker-count decisions, but the active per-data-view fetch executor is still created once with a fixed worker count and is not resized mid-run. v3.4.3 should not present tuner decisions as if they are already an effective live resilience control.

**Guiding principle:** Prefer additive instrumentation over behavioral redesign. If a change requires new scheduling architecture, cross-process telemetry aggregation, or hidden log-routing behavior, defer it.

## Non-Goals

- No batch `ProcessPoolExecutor` rescheduling or mid-run worker-pool resizing
- No attempt to make the current API auto-tuner materially resize active fetch executors
- No worker RSS collection or `--max-memory` feature
- No 429-specific tuning path or circuit-breaker semantics change
- No new heartbeat threads beyond the existing lease-lock heartbeat
- No file-only or JSON-only hidden log channels outside the existing logging setup
- No breaking changes to CLI behavior, exit codes, or run-summary consumers

## 1. Patch-Sized Changes

### 1.1 Structured Diagnostic Event Vocabulary

**Problem:** JSON logs are machine-readable, but there is no stable event vocabulary for filtering resilience and lifecycle transitions that already materially affect runtime behavior.

**Design:**

Add a small diagnostic logging helper in `core/logging.py`:

- `emit_diagnostic(logger, event: str, category: str, **fields)`
- `ContextLoggerAdapter.emit_diagnostic(event: str, category: str, **fields)`

Behavior:

- Logs at `INFO`
- Always includes `event` and `event_category`
- In text mode, formats the message as: `[DIAG] {event}: key=value, ...`
- Nested dict/list fields are compact JSON-encoded in text mode for stable, readable output
- In JSON mode, merges `event`, `event_category`, and fields into the JSON log record
- Works with either `logging.Logger` or `logging.LoggerAdapter`
- Reuses the existing `extra`/formatter/redaction path in `core/logging.py`; diagnostics must not bypass sanitization
- Follows the existing effective log level and `--quiet` behavior; if `INFO` is suppressed, diagnostics are also suppressed

**Initial event catalog** - limited to control points that already have real runtime effect:

| Event | Category | Source | Key Fields |
|------|----------|--------|------------|
| `circuit_breaker_transition` | `resilience` | `api/resilience.py` | `from_state`, `to_state`, `failure_count`, `success_count` |
| `lock_acquired` | `lifecycle` | `core/locks/manager.py` | `lock_path`, `lock_id`, `backend` |
| `lock_released` | `lifecycle` | `core/locks/manager.py` | `lock_path`, `lock_id`, `backend` |
| `lock_acquire_failed` | `lifecycle` | `core/locks/manager.py` | `lock_path`, `backend`, `reason`, `current_owner` |
| `lock_heartbeat_lost` | `lifecycle` | `core/locks/manager.py` | `lock_path`, `lock_id`, `error` |
| `lock_backend_fallback` | `lifecycle` | `core/locks/manager.py` | `from_backend`, `to_backend`, `reason` |
| `shared_cache_summary` | `resource` | `pipeline/batch.py` | `hits`, `misses`, `hit_rate`, `size`, `evictions` |

**Important boundaries:**

- `current_owner` is best-effort metadata from `LockManager.read_info()` / sidecar data only. It remains diagnostic and does not determine lock ownership.
- No new background threads are introduced for logging.
- `lock_backend_fallback` covers both backend-selection fallback in `create_lock_backend()` and acquire-time `fcntl` -> `lease` fallback in `LockManager.acquire()`.
- v3.4.3 does **not** add API auto-tuner diagnostic events. Those should wait for a future release where tuner decisions materially affect active or reused executors.

### 1.2 Org-Report Lock Observability and Stale-Threshold Control

**Problem:** Org-report locking exists today, but the stale-threshold is constructor-only and lock lifecycle visibility is minimal.

**Design:**

1. Add a first-class org-report lock stale-threshold setting:
   - New CLI flag: `--lock-stale-threshold SECONDS`
   - Valid only with `--org-report`
   - Default remains `3600`
   - Reject values `<= 0` with a normal CLI validation error; do not rely on `LockManager`'s internal clamp
   - No env-var contract is introduced in v3.4.3
   - This is **not** a blocking wait timeout. Org-report lock acquisition remains non-blocking. The setting controls stale lease recovery / heartbeat windows and related stale-metadata checks.

2. Extend `OrgReportConfig` with:
   - `lock_stale_threshold_seconds: int = 3600`

3. Wire the value through the existing org-report path:
   - `cli/parser.py` parses `--lock-stale-threshold`
   - `generator.py` validates it for org-report mode and passes it into `OrgReportConfig`
   - `run_org_report()` passes the populated `OrgReportConfig` into `OrgComponentAnalyzer`
   - `OrgComponentAnalyzer` constructs `OrgReportLock(..., stale_threshold_seconds=self.config.lock_stale_threshold_seconds)`
   - `OrgReportLock` forwards it to `LockManager(stale_threshold_seconds=...)`

4. Improve lock contention diagnostics:
   - When lock acquisition fails, use best-effort metadata from `LockManager.read_info()` to surface `pid`, `owner`, `backend`, and `started_at` when available
   - Extend `ConcurrentOrgReportError` with additive optional fields for `lock_holder_owner` and `lock_backend`
   - Preserve the current failure mode as a normal error / exception path; do not block, poll, or change ownership semantics
   - Ensure the default user-facing error path includes those additive fields when available, since org-report failures are currently rendered from the exception message

5. Emit diagnostic events from the actual lock lifecycle:
   - successful acquire
   - release
   - contention / acquire failure
   - lease heartbeat loss
   - backend selection fallback, including `fcntl` -> `lease`

6. Capture additive lock execution details for the run summary at the point where lock state is known:
   - Keep `run_org_report()`'s existing public return contract of `(success, thresholds_exceeded)`
   - Add an optional mutable `runtime_details` sink parameter (default `None`) so direct callers and existing tests remain source-compatible
   - `OrgComponentAnalyzer` owns the authoritative lock runtime state during execution, and `run_org_report()` copies that additive data into the sink in both success and handled-error paths
   - `generator.py` passes a sink and merges it into `run_state["details"]` rather than reconstructing lock state after the fact
   - This payload must distinguish both contention-at-startup and acquired-then-lost execution paths

**Example lock diagnostic event:**

```json
{
  "event": "lock_acquire_failed",
  "event_category": "lifecycle",
  "lock_path": "/Users/example/.cja_auto_sdr/locks/org_report_acme.lock",
  "backend": "lease",
  "reason": "contended",
  "current_owner": {
    "pid": 12345,
    "owner": "acme@AdobeOrg",
    "backend": "lease",
    "started_at": "2026-03-15T10:42:11+00:00"
  }
}
```

### 1.3 `--explain-exit-code CODE`

**Problem:** `--exit-codes` prints the full reference table, but operators and CI users often need a focused explanation for one observed code.

**Design:**

Add a new standalone flag:

```bash
uv run cja_auto_sdr --explain-exit-code 2
```

Behavior:

- Accepts one integer exit code
- Prints a human-readable explanation to stdout
- Exits `0`
- Covers:
  - `0`
  - `1`
  - `2`
  - `3`
  - `130`
  - shell-style signal exits `129-192`
- Unknown codes return a generic explanation plus guidance to inspect `--run-summary-json`

**Architecture requirement:** This is implemented with one shared explainer in `src/cja_auto_sdr/core/exit_codes.py`, then used from both:

- the lightweight fast-path layer in `src/cja_auto_sdr/__main__.py` for standalone explanatory calls
- `src/cja_auto_sdr/generator.py` for parity when fast-path deferral occurs
- Reuse the existing signal helpers in `core/exit_codes.py` rather than duplicating 128+N logic in multiple files
- Add a distinct `RunMode.EXPLAIN_EXIT_CODE` so deferred generator handling preserves accurate `run_state["mode"]` / run-summary metadata instead of collapsing into `exit_codes` or `unknown`

**Fast-path rule:** Mirror the existing fast-path discipline. Only standalone, parser-valid explanatory requests should be intercepted in `__main__.py`. Mixed flags, parse errors, and any invocation containing `--run-summary-json` must defer to `generator.main()` so parser precedence and run-summary behavior stay consistent.

**CLI validation rule:** `--explain-exit-code` is an offline utility mode, like `--exit-codes`. It does not accept positional data view arguments and must not be combined with operational modes such as SDR generation, diff/snapshot modes, org-report modes, discovery/inspection commands, profile-management commands, config validation, or other early-exit utility modes. The only intentional companion flag in v3.4.3 is `--run-summary-json`, which is allowed solely so the invocation can emit a structured run summary for the explanatory call.

**Run-summary interaction:** Standalone `--explain-exit-code CODE` writes the explanation to stdout and exits `0`. When `--run-summary-json -` or `stdout` is also present, the invocation must follow the existing run-summary stdout contract in `generator.main()`: structured run-summary JSON remains the only stdout payload, and the human-readable explanation is emitted via the redirected status stream (stderr in that case).

**Example output:**

```text
Exit code 2: Policy threshold exceeded

Meaning:
  A policy or governance condition failed, but the CLI did not crash.

Common causes:
  - Diff mode found changes
  - --fail-on-quality threshold was reached
  - --fail-on-threshold was reached in org-report mode

Automation guidance:
  Treat as actionable, not as an infrastructure failure.
  Parse --run-summary-json for structured context when available.
```

### 1.4 Run Summary Details Enrichment

**Problem:** The run summary already exists and is widely used, but it does not clearly capture a few operator-relevant execution settings and lock outcomes for troubleshooting.

**Design:**

Keep `summary_version` at **`1.1`** in v3.4.3. The patch only adds new optional keys inside the existing additive `details` payload.

Implementation notes:

- `generator.py` must merge new `details.execution_settings` / `details.lock` keys into existing mode-specific details rather than overwriting `operation_success`, `thresholds_exceeded`, or similar fields
- Add a small helper in `generator.py` for additive `details` merging so early exits and org-report mode do not keep open-coding dict replacement
- Org-report lock details are propagated from the org-report runtime path; they are not inferred from final exit status alone
- `cli/execution.py` should return normalized execution metadata from the effective preparation path rather than requiring late reconstruction from raw CLI args
- Keys remain optional and mode-specific; non-org-report runs do not need to emit a `lock` block

New additive `details` keys:

- `execution_settings`
  - `batch_workers_requested` (`"auto"` or explicit integer request)
  - `batch_workers_effective` (resolved integer worker count after auto-detection)
  - `api_auto_tune_requested`
  - `circuit_breaker_enabled`
  - `shared_cache_active`
  - `org_lock_stale_threshold_seconds` (org-report mode only)
- `lock`
  - `backend`
  - `acquired`
  - `stale_threshold_seconds`
  - `contention_observed`
  - `lost_during_run`
  - `loss_reason` (optional)

**Scope limits:**

- No top-level `telemetry` block in v3.4.3
- No per-worker RSS or process memory data
- No cross-process aggregation collector
- No tuner decision counters or worker-scale telemetry until executor behavior is materially observable
- No per-result API call counts or retry counts

This keeps the patch additive and aligned with the current run-summary ownership while still reflecting effective runtime state rather than raw operator intent alone.

**Field semantics:**

- `shared_cache_active` reflects effective runtime activation, not raw CLI intent. It is `true` only when the batch path actually instantiates the shared cache (currently requiring batch mode, `--shared-cache`, validation caching enabled, and validation not skipped).
- `batch_workers_effective` is the resolved worker count after `auto` handling, not the original CLI token.

**Files touched:**

- `src/cja_auto_sdr/generator.py`
- `src/cja_auto_sdr/cli/execution.py`
- `src/cja_auto_sdr/org/analyzer.py`

## 2. Deferred to a Future Minor Release

These ideas remain worthwhile, but are explicitly **out of scope** for v3.4.3 because they require deeper architectural changes:

- Memory-aware batch backpressure / `--max-memory`
- Worker RSS telemetry returned from batch subprocesses
- Dynamic batch worker-count reduction after executor startup
- Material API auto-tuner telemetry once fetcher behavior can actually apply worker adjustments to active or reused executors
- 429-aware circuit-breaker and tuner redesign

---

## 3. Required Validation

At minimum, update and run targeted tests covering:

- lock manager lifecycle, backend fallback, and heartbeat-loss behavior
- org-report parser validation for `--lock-stale-threshold` and config wiring into `OrgReportConfig`
- org-report contention errors and exception message rendering
- fast-path CLI dispatch for `--exit-codes`, `--explain-exit-code`, and `--run-summary-json` deferral
- deferred `--explain-exit-code` generator handling, including `RunMode.EXPLAIN_EXIT_CODE` run-summary metadata and the stdout/stderr contract when `--run-summary-json -` is present
- parser validation for invalid `--explain-exit-code` combinations, including positional data views and conflicting command modes
- run-summary status inference and additive `details` behavior
- SDR / batch execution-context population for effective runtime settings
- diagnostic logging helper behavior in both text and JSON modes, including adapter support, extra-field merging, and redaction of nested sensitive values
