# v3.4.3 Design Spec: Operational Resilience & Observability

**Date:** 2026-03-15
**Status:** Draft
**Scope:** Patch release — v3.4.1-scale (~500+ new tests, meaningful code changes)
**Theme:** Make the tool harder to break *and* easier to understand when it does

## Motivation

v3.4.0-2 delivered org-report trending, coverage hardening, and agent automation enablement. The tool is feature-complete for its core use cases. v3.4.3 shifts focus inward: hardening the runtime for production workloads (large orgs, long-running jobs, concurrent runs) and giving operators the diagnostics they need to tune, debug, and trust automated runs.

**Guiding principle:** Every resilience mechanism must be observable. Adaptive scaling is only useful if the log tells you it happened.

## Non-Goals

- New user-facing features (no new analysis modes, output formats, or discovery commands)
- Windows-specific hardening (deferred — smoke tests sufficient for now)
- Breaking changes to CLI, run summary schema, or exit codes
- Dependency version bumps or optional dependency expansion

## 1. Operational Resilience

### 1.1 Memory-Aware Batch Processing

**Problem:** `BatchProcessor` uses `ProcessPoolExecutor` with no memory tracking. In large orgs (500+ data views), workers can collectively exhaust available RAM with no warning or mitigation.

**Design:**

1. **Per-worker RSS tracking** — Each worker process calls `resource.getrusage(RUSAGE_SELF)` at completion and reports `peak_rss_kb` back in `ProcessingResult`. On platforms where `getrusage` is unavailable (Windows), return `None` with a debug-level log warning.

2. **New flag: `--max-memory MB`** — Optional memory ceiling for the parent batch orchestrator. Before submitting each new worker task to the executor:
   - Read parent process RSS via `resource.getrusage(RUSAGE_SELF).ru_maxrss`
   - If RSS exceeds 80% of `--max-memory`, pause new task submission until in-flight workers complete (backpressure)
   - If RSS exceeds 95% of `--max-memory`, log a warning and reduce effective max_workers by half for the remainder of the run
   - Never hard-kill workers — backpressure only

3. **Structured diagnostic event** when backpressure activates:
   ```json
   {
     "event": "memory_backpressure",
     "current_rss_mb": 1840,
     "ceiling_mb": 2048,
     "threshold_pct": 80,
     "action": "pause_submission",
     "in_flight_workers": 6
   }
   ```

4. **Run summary integration** — New `telemetry.peak_rss_mb` field (parent process peak) and per-result `peak_rss_kb` (worker process peak).

**Constants:**
- `DEFAULT_MAX_MEMORY_MB = None` (disabled by default)
- `MEMORY_BACKPRESSURE_THRESHOLD_PCT = 80`
- `MEMORY_EMERGENCY_THRESHOLD_PCT = 95`

**Files touched:**
- `core/constants.py` — new constants
- `cli/parser.py` — `--max-memory` flag
- `pipeline/batch.py` — backpressure logic in submission loop
- `pipeline/workers.py` — RSS tracking in worker return value
- `pipeline/models.py` — `peak_rss_kb` field on `ProcessingResult`

### 1.2 Adaptive Worker Scaling with 429 Awareness

**Problem:** `CircuitBreaker` treats HTTP 429 (rate limit) the same as 500 (server error). `APIWorkerTuner` only responds to latency, not rate-limit signals. Under sustained 429 pressure, the tool retries at full concurrency instead of backing off.

**Design:**

1. **429-specific tracking on `CircuitBreaker`:**
   - New `rate_limit_count` counter and `record_rate_limit()` method
   - `record_rate_limit()` increments the counter and applies immediate backoff (doubles the current retry base delay) but does NOT trip the circuit — rate limits are transient, not failures
   - Exposed in `get_statistics()` as `rate_limit_count` and `rate_limit_backoffs`

2. **Rate-limit-aware scaling on `APIWorkerTuner`:**
   - New signal path: if 429 responses exceed 20% of the recent sample window, scale down by 2 workers (instead of the normal 1-at-a-time latency-based scaling)
   - New config field: `rate_limit_scale_down_threshold` (default: 0.20)
   - After rate-limit-triggered scale-down, impose a 30-second cooldown before any scale-up (2x normal cooldown)
   - Recovery: when 429 rate drops below 5% for a full sample window, resume normal scaling behavior

3. **Structured diagnostic events:**
   ```json
   {
     "event": "rate_limit_backoff",
     "rate_429_pct": 25,
     "sample_window_size": 5,
     "workers_before": 8,
     "workers_after": 6,
     "cooldown_seconds": 30
   }
   ```

**Constants:**
- `RATE_LIMIT_SCALE_DOWN_THRESHOLD = 0.20`
- `RATE_LIMIT_RECOVERY_THRESHOLD = 0.05`
- `RATE_LIMIT_COOLDOWN_MULTIPLIER = 2`
- `RATE_LIMIT_SCALE_DOWN_STEP = 2`

**Files touched:**
- `core/constants.py` — new constants
- `api/resilience.py` — `record_rate_limit()`, updated `get_statistics()`
- `api/tuning.py` — 429-aware scaling path, extended cooldown logic

### 1.3 Lock Hardening for Concurrent/NFS Usage

**Problem:** Lock lifecycle events are silent. Stale lock reclaim happens without logging who owned the stale lock. Lock staleness threshold requires env var configuration — no CLI flag.

**Design:**

1. **Structured lock lifecycle events** — Log at INFO level for all lock state transitions:

   | Event | Fields |
   |-------|--------|
   | `lock_acquired` | `lock_id`, `backend`, `acquire_duration_ms` |
   | `lock_released` | `lock_id`, `backend`, `held_duration_ms` |
   | `lock_stale_reclaimed` | `lock_id`, `previous_owner` (full `LockInfo`), `stale_age_seconds` |
   | `lock_heartbeat_lost` | `lock_id`, `last_heartbeat_at`, `expected_interval_s` |
   | `lock_acquire_failed` | `lock_id`, `current_owner` (from sidecar), `reason` |

2. **New flag: `--lock-timeout SECONDS`** — Maps to the existing `stale_threshold_seconds` parameter. Default: 3600 (unchanged). Surfaces the existing env var (`CJA_LOCK_STALE_THRESHOLD`) as a first-class CLI option.

3. **Run summary lock stats:**
   ```json
   {
     "lock_stats": {
       "acquire_duration_ms": 15,
       "backend": "fcntl",
       "heartbeat_count": 42,
       "stale_reclaims": 0
     }
   }
   ```

**Files touched:**
- `cli/parser.py` — `--lock-timeout` flag
- `core/locks/manager.py` — structured log events at each transition
- `core/locks/backends.py` — pass previous `LockInfo` to reclaim log

### 1.4 Long-Running Job Heartbeat Logging

**Problem:** Batch jobs running for 30+ minutes produce no intermediate structured output. Log aggregation systems (ELK, CloudWatch) see silence until completion or failure.

**Design:**

1. **Batch heartbeat thread** — In `BatchProcessor.process_batch()`, start a daemon thread that emits a structured log event at a fixed interval:
   ```json
   {
     "event": "batch_heartbeat",
     "completed": 45,
     "total": 200,
     "failed": 2,
     "in_flight": 6,
     "elapsed_seconds": 360,
     "estimated_remaining_seconds": 440,
     "peak_rss_mb": 1200
   }
   ```

2. **Interval configuration** — Default 60 seconds, configurable via `CJA_HEARTBEAT_INTERVAL_SECONDS` env var. Minimum 10 seconds, maximum 600 seconds.

3. **Single-DV heartbeat** — For single data-view processing with large component counts (>500 components), emit a heartbeat during the API fetch phase at the same interval. Includes `components_fetched` / `components_total` progress.

4. **Console suppression** — Heartbeats go to the structured log file and JSON log format only. They do NOT appear on the console (would conflict with tqdm progress bar). When `--log-format json` is used with `--quiet`, heartbeats appear on stderr.

**Constants:**
- `DEFAULT_HEARTBEAT_INTERVAL_SECONDS = 60`
- `MIN_HEARTBEAT_INTERVAL_SECONDS = 10`
- `MAX_HEARTBEAT_INTERVAL_SECONDS = 600`
- `HEARTBEAT_COMPONENT_THRESHOLD = 500`

**Files touched:**
- `core/constants.py` — heartbeat constants
- `pipeline/batch.py` — heartbeat daemon thread
- `api/fetch.py` — single-DV fetch phase heartbeat

## 2. Developer/User Experience

### 2.1 Enhanced Run Summary with Resource Telemetry

**Problem:** The current run summary (schema v1.1) captures results and environment but no resource usage, API behavior, or timing breakdown. Operators can't diagnose *why* a run was slow or whether it was close to failure.

**Design:**

Bump `RUN_SUMMARY_SCHEMA_VERSION` to `"1.2"`. Add a `telemetry` block (all fields optional — absent if data unavailable):

```json
{
  "telemetry": {
    "peak_rss_mb": 245.3,
    "api_calls_total": 847,
    "api_calls_retried": 12,
    "api_429_count": 3,
    "circuit_breaker_trips": 0,
    "worker_scale_adjustments": [
      {
        "at_seconds": 45.2,
        "from": 8,
        "to": 6,
        "reason": "rate_limit_backoff"
      }
    ],
    "cache_hits": 34,
    "cache_misses": 12,
    "cache_hit_rate": 0.739,
    "lock_stats": {
      "acquire_duration_ms": 15,
      "backend": "fcntl",
      "heartbeat_count": 42,
      "stale_reclaims": 0
    },
    "phase_durations": {
      "config_validation": 0.8,
      "api_fetch": 45.2,
      "quality_validation": 3.1,
      "output_generation": 12.4
    }
  }
}
```

Per-result entries in `results[]` gain:
- `peak_rss_kb` (worker process, batch mode only)
- `api_calls` (count for this data view)
- `api_retries` (retry count for this data view)

**Backward compatibility:** New fields are purely additive. Schema version bump signals availability but does not break v1.1 consumers.

**Implementation approach:**
- Introduce a `TelemetryCollector` class that accumulates stats throughout execution
- Pass it through `WorkerArgs` and `run_state`
- `_build_run_summary_payload()` calls `collector.to_dict()` to populate the telemetry block
- Thread-safe: uses `threading.Lock` for counters updated from multiple workers

**Files touched:**
- `core/constants.py` — `RUN_SUMMARY_SCHEMA_VERSION = "1.2"`
- New file: `core/telemetry.py` — `TelemetryCollector` class
- `pipeline/models.py` — new fields on `ProcessingResult`
- `pipeline/batch.py` — wire collector through batch loop
- `pipeline/single.py` — wire collector through single-DV processing
- `generator.py` — updated `_build_run_summary_payload()`

### 2.2 Structured Diagnostic Log Events

**Problem:** Logging is traditional Python logging with no structured event vocabulary. In JSON log mode, events are untyped — operators can't filter by event category in their log aggregation pipeline.

**Design:**

Define a diagnostic event vocabulary. All events:
- Logged at INFO level via `ContextLoggerAdapter`
- Include an `"event"` key for filtering
- Include a `"event_category"` key: `"resilience"`, `"resource"`, `"progress"`, `"lifecycle"`
- Are structured JSON when `--log-format json`, prefixed human-readable lines in text mode

**Event catalog:**

| Event | Category | When Emitted | Key Fields |
|-------|----------|--------------|------------|
| `worker_scale_adjustment` | resilience | APIWorkerTuner changes count | `from`, `to`, `reason`, `trigger_value` |
| `memory_backpressure` | resource | RSS approaches ceiling | `current_rss_mb`, `ceiling_mb`, `action` |
| `rate_limit_backoff` | resilience | 429 rate exceeds threshold | `rate_429_pct`, `workers_before`, `workers_after` |
| `circuit_breaker_trip` | resilience | Circuit opens | `failure_count`, `threshold`, `last_error_type` |
| `circuit_breaker_recovery` | resilience | Circuit closes | `success_count`, `downtime_seconds` |
| `lock_acquired` | lifecycle | Lock obtained | `lock_id`, `backend`, `acquire_duration_ms` |
| `lock_released` | lifecycle | Lock freed | `lock_id`, `held_duration_ms` |
| `lock_stale_reclaimed` | lifecycle | Stale lock taken over | `lock_id`, `previous_owner`, `stale_age_s` |
| `cache_summary` | resource | End of API fetch phase | `hits`, `misses`, `hit_rate`, `evictions` |
| `batch_heartbeat` | progress | Every N seconds in batch | `completed`, `total`, `failed`, `elapsed_s` |
| `phase_transition` | progress | Between processing phases | `phase`, `duration_seconds` |

**Implementation approach:**
- Add `emit_diagnostic(event: str, category: str, **fields)` helper on `ContextLoggerAdapter`
- In text mode, format as: `[DIAG] {event}: {key}={value}, ...`
- In JSON mode, merge event fields into the JSON log line with `event` and `event_category` keys

**Files touched:**
- `core/logging.py` — `emit_diagnostic()` method
- All files from Sections 1.1-1.4 emit events via this method

### 2.3 `--explain-exit-code CODE` Helper

**Problem:** CI/CD operators see `exit code 2` in their pipeline and have to search documentation to understand what it means. The orchestrator shell templates handle this, but standalone usage has no quick reference.

**Design:**

New standalone flag `--explain-exit-code CODE`:
- Accepts an integer exit code
- Prints a human-readable explanation to stdout and exits with code 0
- Covers: 0, 1, 2, 3, 130 (SIGINT), and the 128+N signal range
- Includes: meaning, common causes, recommended automation response, and cross-reference to `--run-summary-json`

Example output:
```
Exit code 2: Policy threshold exceeded

Common causes:
  - Diff comparison found changes between data views or snapshots
  - Quality gate severity threshold was breached (--fail-on-quality)
  - Org governance threshold was exceeded (--fail-on-threshold)

In automation:
  - Treat as actionable: open issue, send alert, or block merge
  - Parse --run-summary-json for structured failure details
  - Check failure_code field for specific failure classification

See also:
  - docs/FAILURE_CODES.md for the failure code registry
  - docs/TROUBLESHOOTING.md for diagnosis workflows
```

For unknown codes, print a generic message suggesting `--run-summary-json` and `--log-level DEBUG`.

**Files touched:**
- `cli/parser.py` — new `--explain-exit-code` argument
- `core/exit_codes.py` — `explain_exit_code(code: int) -> str` function with explanation registry
- `cli/main.py` — early dispatch (before profile resolution)

### 2.4 Performance Tuning Guide

**New file:** `docs/PERFORMANCE_TUNING.md`

**Contents:**

1. **Org-size recommendation matrix** — Table mapping org size (10/50/100/500/1000+ data views) to recommended `--workers`, `--sample`, and expected memory usage
2. **Flag interaction guide** — How `--workers`, `--sample`, `--cache-max-age`, and `--max-memory` compose; which combinations are redundant or conflicting
3. **Memory budgeting** — RSS-per-worker heuristic (base ~80MB + ~2MB per 100 components), how to use `--max-memory` effectively, reading `telemetry.peak_rss_mb` from run summaries
4. **API quota estimation** — Expected API calls per data view (~3-5 base + 1 per inventory module enabled), how retries and 429s multiply the total, safe `--workers` count formula
5. **Reading phase durations** — How to identify bottlenecks from `telemetry.phase_durations` in run summary
6. **Troubleshooting slow runs** — Decision tree: API-bound vs. memory-bound vs. output-bound, with remediation for each

### 2.5 Automation Debugging Guide

**New file:** `docs/DEBUGGING_AUTOMATION.md`

**Contents:**

1. **Reading orchestrator logs** — Field-by-field explanation of structured log events, filtering by `event_category`
2. **Reproducing CI failures locally** — Extract environment and arguments from `--run-summary-json`, replay with `--dry-run` and `--log-level DEBUG`
3. **Common failure patterns:**
   - Stale locks from killed cron jobs (symptoms, diagnosis, `--lock-timeout` fix)
   - 429 storms in high-concurrency batch runs (symptoms, diagnosis, worker tuning)
   - Memory exhaustion in large orgs (symptoms, diagnosis, `--max-memory` and `--sample`)
   - Intermittent API timeouts (circuit breaker behavior, retry escalation)
4. **Exit code decision tree** — Flowchart: exit code -> likely cause -> remediation steps
5. **Log aggregation setup** — Example configurations for shipping `--log-format json` output to ELK, CloudWatch, Datadog

### Coverage Targets

- Maintain 95%+ gate (`.github/workflows/tests.yml`)
- Target 97%+ actual (matching v3.4.1-2 trajectory)
- New modules (`core/telemetry.py`) target 100% branch coverage
- All diagnostic events validated in both text and JSON log formats

### Test Patterns

- **Memory tests:** Mock `resource.getrusage()` to simulate RSS values; verify backpressure triggers at correct thresholds
- **429 tests:** Mock API responses with configurable 429 rates; verify worker scaling and cooldown timing
- **Lock tests:** Use `multiprocessing` to simulate concurrent lock acquisition; verify stale reclaim with synthetic `LockInfo`
- **Heartbeat tests:** Mock `time.monotonic()` to control interval timing without real delays
- **Telemetry tests:** Run full pipeline with mocked API; verify run summary JSON schema and field population
- **Integration tests:** Compose multiple resilience features in a single batch run; verify they interact correctly (e.g., memory backpressure + 429 scaling + heartbeat all active)

## 6. Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| `resource.getrusage` behavior varies across macOS/Linux (KB vs bytes) | Medium | Platform-detection normalization in worker; unit tests mock both conventions |
| Heartbeat thread interferes with `ProcessPoolExecutor` shutdown | Low | Daemon thread with `Event`-based shutdown signal; tested in isolation |
| `TelemetryCollector` lock contention under high worker counts | Low | Lock scope minimized to counter increments; no I/O under lock |
| Run summary schema v1.2 breaks downstream consumers | Very low | Purely additive fields; version bump is informational only |
| `--max-memory` false positives due to RSS measurement lag | Low | 80% threshold provides headroom; documented as advisory, not precise |
